## 三、需求 6：分隔线可见且不遮挡任务包交互

### 改动

在 `CalendarTab.ets` 新增统一常量：

```typescript
const GRID_LINE_COLOR: string = '#B8B8B8';
```

周视图、日视图的小时线以及 24:00 底边统一使用该颜色。经过两轮实测修订，最终结构为：

1. 删除事件块内部按相对位置重绘的灰线，避免它在缩放时形成第二套坐标并与主网格错位。
2. 每个日期栏只保留一个完整网格，并将其放在事件块上方，保证灰线经过彩色任务包时仍保持灰色。
3. 网格根节点使用 `HitTestMode.Transparent`。ArkUI 官方规则明确：Stack 上层节点要让重叠的下层节点继续参与触摸测试，应使用 `Transparent`，而不是上一版错误采用的 `None`。
4. 事件块外层仍直接持有短按、长按菜单和拉伸手势。

### 取舍

没有引入 Canvas，也不再维护事件内部线段数组。唯一网格直接使用与时间标签、事件块相同的 `weekHourHeight` / `dayHourHeight`，因此缩放时不存在两套线段各自换算的问题。

## 四、需求 2：周/日时间轴双指缩放

### 状态与范围

- 周视图：`weekHourHeight`
- 日视图：`dayHourHeight`
- 最小高度：45vp/小时
- 最大高度：150vp/小时
- 手势：`PinchGesture({ fingers: 2 })`

### 缩放锚点

捏合开始时记录：

- 当前小时高度
- 当前 `Scroller` 的 Y 偏移
- 捏合中心对应的分钟数

更新缩放时重新计算滚动位置，使捏合中心对应的时间点尽量保持在原屏幕位置，减少内容跳动。

反馈修订中补充了两项校正：

- 锚点换算和反算都纳入 `GRID_LINE_OFFSET`，避免固定的 3vp 网格偏移在倍率变化时累积为漂移。
- 每次 `onActionUpdate` 先立即执行一次 `Scroller.scrollTo()`，让手指当前帧就锚定原时间；同时每帧最多排队一个布局后复校任务，该任务读取最新目标偏移。上一版“不断取消并重排延后任务”的写法已删除，避免连续捏合时直到手势结束才滚动。

事件块顶部计算现在显式接收时间轴 `startHour`，与网格及“现在”时间线共享同一坐标原点；当前周/日视图均从 00:00 开始，后续即使调整周视图起始时间也不会再次出现坐标系分叉。

### “现在”时间线平滑更新

- 新增 `nowSecond`，时间线位置使用“小时 + 分钟 + 秒/60”计算。
- 刷新周期由 60 秒改为 1 秒；在 150vp/小时的最大倍率下，每秒位移也只有约 0.042vp，肉眼呈现为连续推进。
- 删除每秒包裹红线位置更新的 `UIContext.animateTo`。显式动画与捏合同时修改同一个纵向位置时会保留旧动画目标，是红线缩放漂移的重要原因。标签仍保持 `HH:mm`。
- `aboutToDisappear()` 会清理时间定时器及尚未执行的缩放校正任务，避免离开页面后重复刷新或积累回调。

2026-09-09 继续定位到一个 ArkUI 响应式边界：原 `buildTimeIndicator(hourHeight, startHour)` 是带两个值参数的私有 `@Builder`。HarmonyOS 文档说明，此类参数按值传递，不会因为调用方 `@State` 在捏合中变化而自动驱动 Builder 内部刷新。因此静态位置和切换视图后的重建正常，但连续缩放期间红线仍可能使用旧高度。

本轮将其改为无参数 `buildTimeIndicator()`，在 Builder 内直接通过 `this.viewMode` 读取 `this.weekHourHeight` / `this.dayHourHeight` 及对应起始小时。这样红线位置与网格、事件块共享当前缩放状态并参与同一轮响应式重绘；秒级刷新逻辑继续保留。本项已完成编译验证，仍需在设备上确认捏合过程中的实时效果。

### 同步变化

小时高度变化会同时驱动：

- 左侧时间标签间距
- 右侧固定网格
- 事件块 `top` 与 `height`
- 当前时间指示线
- 拖拽时间换算
- 步骤摘要最大行数

步骤摘要会随事件块变高逐步显示更多行，缩小时自动收敛。

### 顺带修复

周/日拖拽放下不再把滚动偏移写死为 0，而是读取对应 `Scroller.currentOffset().yOffset`，修复滚动后排程时间偏移的问题。

## 五、需求 3：事件块长按菜单（实现尝试未通过设备验收）

以下内容记录此前的实现尝试，不代表功能已经完成。2026-09-09 设备反馈为：任务包内静止按住约 400ms 后没有显示二级菜单。因此需求已在 `left_problem.md` 重新打开，后续需要从实际手势竞争和菜单展示链路重新验证。

事件块不再直接依赖 `bindContextMenu(..., ResponseType.LongPress)` 的内置识别器，而是把“识别长按”和“显示菜单”拆开：

- `priorityGesture(LongPressGesture(...))` 负责识别静止长按，持续时间 400ms。
- `allowableMovement = 18px` 容忍按住时的细微手抖；移动超过阈值后长按失败，父级 `Scroll` 接管，所以从任务包内部起手也能滑动时间轴。
- 长按成功后写入 `contextMenuEventId`，由 `bindContextMenu(isShown, ...)` 显示对应任务包的菜单。
- 菜单消失或执行菜单项时清空 ID，避免残留显示状态。

短按仍打开详情，菜单仍提供：

### 复制

- 深拷贝当前日程及步骤。
- 进入“待复制”状态并显示提示条。
- 点击周/日时间轴的目标位置后创建新 ID 的日程。

### 剪切

- 保存当前日程快照，但在选择目标前不删除原日程。
- 点击目标位置后保留原 ID，更新日期与开始/结束时间。
- 这种实现避免用户取消剪切时丢失原数据。

### 分享

- 使用 `@kit.ShareKit` 的 `systemShare.SharedData` 与 `ShareController`。
- 分享内容为纯文本，包括任务包名称、日期、起止时间和步骤明细。
- 由 HarmonyOS 系统分享面板选择目标渠道。

### 拉伸

- 进入事件块拉伸模式。
- 事件块显示白色边框和上下拖动手柄。

## 六、需求 4：事件块拉伸与步骤等比缩放（功能链不可达）

以下内容记录已写入的状态、手柄和计算逻辑。由于需求 3 的菜单入口没有在设备上出现，拉伸模式无法进入，上下手柄也未能被用户看到和操作，故不能视为已完成；已在 `left_problem.md` 重新列为待办。

### 交互语义

- 拖动上边界：改变开始时间，保持原结束时间不变。
- 拖动下边界：保持开始时间不变，改变总时长。
- 时间以 5 分钟为单位吸附。
- 手势取消时恢复预览，不写入持久化。
- 手势结束时才调用 `ScheduleStore.updateEvent()` 一次性落盘，避免拖动过程中频繁写 Preferences。

### 步骤缩放

步骤时长以目标总时长与原总时长的比例计算：

```text
新步骤时长 ≈ 原步骤时长 × 新总时长 / 原总时长
```

实现约束：

- 每个步骤至少 1 分钟。
- 前面的步骤四舍五入。
- 最后一个步骤补齐差额。
- 所有步骤之和严格等于事件目标总时长。
- 只修改 `ScheduledEvent.steps` 的深拷贝，不修改 `TaskPackage.steps` 模板。

## 十三、周/日视图重叠日程处理（2026-09-12）

本轮处理周视图和日视图中任务包互相遮挡的问题，并在写入日程前限制一个重叠组最多包含两个任务包。修改集中在 `entry/src/main/ets/pages/CalendarTab.ets`，没有改变持久化数据结构。

### 1. 重叠判定与容量规则

- 统一将日程时间看作半开区间 `[开始时间, 结束时间)`；例如 09:00-10:00 与 10:00-11:00 首尾相接，不算重叠。
- 结束时间仍以 `ScheduledEvent.steps` 的总分钟数为准，避免跨过午夜时仅凭取模后的 `endHour` 得出错误结果。
- 一个重叠组最多有两个成员。候选日程同时碰到两个既有日程，或者碰到的既有日程已经与另一项重叠，都会被视为第三项并拒绝。
- 拦截提示统一为“该时段已有两个任务包，不能继续安排”；拉伸路径使用“该时段已有两个任务包，无法拉伸到此处”。
- 容量检查覆盖三个会改变时间位置的入口：从左侧拖入新日程、复制/剪切后的粘贴、拉伸结束提交。剪切时会排除源日程自身，避免把自己错误计入重叠数量。
- 粘贴被拒绝后保留待粘贴状态，用户可以直接改选其他时间；拉伸被拒绝后恢复持久化中的原日程。

之所以限制整个重叠组而不只限制某一瞬间的并发数，是为了避免 A 与 B 重叠、B 与 C 重叠这类链式三项数据。链式数据虽然可能没有“三项同时重叠”的瞬间，但周视图仍无法稳定表达为一张只含两个标题的合并卡。

### 2. 周视图：两个日程合成一张卡

- 渲染前按开始时间排序并配对重叠日程，配对后只创建一张显示卡，不再依靠 `Stack` 的先后顺序互相覆盖。
- 合并卡的顶部取两个任务中较早的开始时间，底部取较晚的结束时间，保证两项原本覆盖的时间范围都可见。
- 背景颜色来自总时长更长的任务；时长相同时使用时间排序靠前的任务颜色。
- 为适应周视图窄列，合并卡隐藏步骤摘要，只保留两项任务标题。标题上下排列，第二项前单独显示正常字重的“和”，任务标题保持粗体。
- 合并卡内部的两行各自保留点击和长按绑定，因此用户仍能区分并操作对应的日程实例。
- 未发生重叠的日程继续沿用原卡片布局、步骤摘要、点击、长按和拉伸手柄逻辑。

### 3. 日视图：重叠日程左右并排

- 为当天日程按开始时间排序，再使用两列贪心分配：优先放入已经空闲的左列，否则放入右列。
- 只要某项与当天另一项重叠，该项宽度改为约半宽；左右两列之间保留细小间距。
- 两个卡片的纵向起点和高度仍分别使用自己的开始时间与持续时长计算，因此并排后不会被强制拉成相同长度。
- 没有重叠的日程保持原来的全宽显示。

### 4. 验收场景

1. 周视图安排 09:00-11:00 与 10:00-10:30：应显示一张覆盖 09:00-11:00 的合并卡，背景使用 2 小时任务的颜色，正文为两个标题且“和”不加粗。
2. 日视图查看同一数据：两项应左右并排，一项保持 2 小时高度，另一项保持 30 分钟高度。
3. 再拖入一个与该组任一成员重叠的任务：不新增日程，并显示容量提示。
4. 安排 09:00-10:00 与 10:00-11:00：两项不应被判为重叠。
