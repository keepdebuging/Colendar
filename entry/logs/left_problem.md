## 需求 0（Bug）：编辑任务包后，时间轴标签/事件块长度不即时刷新

### 现象

- 在日历**周/日视图**里点击事件块（或左侧任务包卡片）→ 详情弹窗 →「✏ 编辑」→ 修改步骤时长/数量 →「保存」→ `router.back()` 返回日历。
- 返回后**时间轴不即时更新**：被编辑任务包对应的事件块高度（`getTotalDuration(steps) / 60 × hourHeight`）及其所在小时槽位的高度（`dayHourHeights` / `weekHourHeights`，即左侧时间标签的间距）仍是旧值。
- 只有**切换视图（月/周/日）或切换 Tab 再切回来**之后，长度才会更新。

### 数据层（已正确，无需改）

`taskStore.updatePackage()` 内部已调用 `scheduleStore.syncPackageFields(updatedPkg)`（见 `log_08`），把日程里冗余的 `steps` / `endHour` / `endMinute` 一并更新。因此 `scheduleStore.events` 里的数据是**最新**的——问题不在数据，而在 UI 层没有在返回时重新计算/重绘时间轴。

### 根因

时间轴的高度依赖两个 `@State` 数组 `dayHourHeights` / `weekHourHeights`，它们只在以下时机被重算：

1. `loadData()`（内部调用 `computeDayHourHeights()` 与 `buildWeekData()` → `computeWeekHourHeights()`），由 `@Consume @Watch('loadData') refreshTrigger` 触发。
2. 各类导航/视图切换方法（`switchToView` / `goToDayView` / `goToNextDay` / `goToNextWeek` 等）直接调用 `computeXXXHourHeights()`。

编辑返回时，本应由 `Index.onPageShow()` 递增 `refreshTrigger` → 触发 `CalendarTab.loadData()` 重算高度。但实测该链路在「从编辑页 `router.back()` 返回」时**没有即时生效**：`dayHourHeights` / `weekHourHeights` 保持旧值，导致时间轴标签间距与事件块槽位高度都不变；直到切换视图/Tab（触发 `onChange` / `switchToView` 的重算或 `build()` 重建）才恢复。

> 补充：事件块**自身**高度是内联计算的（`getTotalDuration(evt.steps)/60 × hourHeight`），只要 `build()` 重跑就会读到最新数据；真正的瓶颈是**外层槽位高度**（`dayHourHeights[hour]` / `weekHourHeights[hour]`）没更新，新高度的事件块会被旧高度的槽位裁切。这也是「切换视图能恢复」的原因——`viewMode` 变化强制 `build()` 重建，重新读到最新的事件数据。

### 修复方向

1. **定位断点**：在 `Index.onPageShow()` 与 `CalendarTab.loadData()` 各加一行日志，确认「返回 → `onPageShow` 是否触发 → `refreshTrigger` 是否自增 → `loadData` 是否被调用」。
   - 若 `onPageShow` 未触发：返回刷新不能再依赖 `onPageShow`，改走更可靠的触发（见 3）。
   - 若 `loadData` 已调用但 UI 未变：检查 `@Consume @Watch` 在 `TabContent` 嵌套下是否失效，或 `dayHourHeights` 数组重新赋值是否未触发重渲染。

2. **最小修复**：确认返回时 `CalendarTab.loadData()` 确实执行（它已包含 `computeDayHourHeights()` + `computeWeekHourHeights()`），即可让时间轴即时刷新。

3. **兜底方案（推荐）**：不依赖 `onPageShow`，让日历直接感知数据变化——给 `ScheduleStore` 增加一个可被 `CalendarTab` 订阅的版本号/回调（`syncPackageFields` 时自增），`CalendarTab` 观察到变化后主动 `this.schedules = [...scheduleStore.events]` 并调用 `computeDayHourHeights()` / `computeWeekHourHeights()`。这样无论从哪条路径编辑返回，时间轴都会即时刷新。

### 涉及文件

- `entry/src/main/ets/pages/Index.ets`（`onPageShow` → `refreshTrigger`）
- `entry/src/main/ets/pages/CalendarTab.ets`（`loadData` / `computeDayHourHeights` / `computeWeekHourHeights`）
- `entry/src/main/ets/models/ScheduledEvent.ets`（若采用兜底方案，新增订阅/版本号）

## 需求 1：事件块跨小时分隔线显示

### 现状

- 事件块高度**已经**按时间映射：`height = getTotalDuration(steps) / 60 × hourHeight`。日视图 `hourHeight = 60` 时，1h15m = 75vp，映射正确。
- **问题在于定位**：事件块被「装」在 `startHour` 对应的单个槽位 `Column` 里（`getHourEvents(hour)` / `getEventsForDateAndHour(dateStr, hour)` 按 `startHour === hour` 过滤）。
- 结果：跨小时事件（如 15:00 起、90 分钟）会把 15:00 槽位撑大到 90vp（`computeXXXHourHeights` 取事件块高度的最大值），导致该小时分隔线被「撑开」、整体错位，而不是让事件块正确覆盖到 16:00 分隔线之上。

### 目标

- 事件块根据 `startHour` / `startMinute` 与总时长，用**绝对定位**精确覆盖在时间轴上，正确跨越小时分隔线。
- 分隔线（网格）位置固定，不随事件块的存在而变化。

### 技术要点

- 把事件块渲染从「流式槽位」改为「Stack 绝对定位」：
  - **背景层**（标签列 + 水平分割线）保持流式布局，固定高度 = `24 × hourHeight`。
  - **事件块层**用 `.position({ x, y })` + `.height(duration/60 × hourHeight)` 覆盖在背景层之上。
  - 垂直坐标：`top = (startHour × 60 + startMinute) / 60 × hourHeight`。
  - 周视图还需按天定位水平 `x`（7 列均分，可用 `Column().width('calc((100%-36px)/7)')` 或 `layoutWeight` 计算每列偏移）。
- 移除 `computeWeekHourHeights` / `computeDayHourHeights` 中「按事件块撑大槽位」的逻辑——槽位高度恢复为标准 `hourHeight`（跨分隔线后无需动态高度）。
- 涉及文件：`CalendarTab.ets` 的 `buildWeekContent` / `buildDayContent`、`computeXXXHourHeights`；数据模型 `ScheduledEvent`（已含 `startHour`/`startMinute`/`endHour`/`endMinute`/`steps`，无需改动）。

### 待确认点

- 同一小时内多个事件、跨小时事件重叠时的视觉处理（是否允许重叠、是否需要左右错开）。
- 非整点开始（如 `startMinute = 30`）的事件，事件块顶部是否需落在半格位置（当前 `computeXXXHourHeights` 只按小时粒度）。

## 需求 2：双指缩放（视图 + 任务包同步）（🔄 当前时间线修正待设备复验，详见 `log_11.md`）

> 周/日视图分别维护 45~150vp 的小时高度；捏合锚点纳入网格基准偏移，每帧立即校正 Scroller 并在布局后使用最新目标复校。2026-09-09 又将当前时间线从“向 `@Builder` 传入小时高度值”改为“无参数 Builder 直接读取当前 `@State` 小时高度”，使它在捏合时进入同一响应式重绘链路。当前时间线每秒刷新，不再使用会与缩放竞争位置的显式动画；代码已构建通过，实时联动效果待设备复验。

### 现状

- 小时高度是常量：`WEEK_HOUR_HEIGHT = 42`、`DAY_HOUR_HEIGHT = 60`。

### 目标

- 周/日视图支持双指捏合缩放，小时标签高度在 **45vp ~ 150vp** 之间连续变化。
- **视图与任务包同步缩放**：放大视图时任务包（事件块）等比例放大，从而能显示更多步骤文字（步骤列表行数随高度自适应）；缩小则相反。

### 技术要点

- 把 `WEEK_HOUR_HEIGHT` / `DAY_HOUR_HEIGHT` 改为 `@State` 变量（如 `weekHourHeight` / `dayHourHeight`）。
- 用 `PinchGesture`（`PinchGesture({ fingers: 2 })`，`onActionUpdate` 读 `event.scale`）累乘缩放比例，映射并 clamp 到 45~150vp。
- 缩放后重新计算槽位高度数组 + 事件块位置（与需求 1 的绝对定位联动，`top`/`height` 都随 `hourHeight` 重算）。
- **事件块内容自适应**：事件块高度随 `hourHeight` 增大后，步骤列表的显示行数（当前 `maxLines(1~2)`）应动态放宽，以展示更多步骤。
- 缩放锚点：以捏合中心所在时间点锚定，避免缩放时内容跳变（可记录缩放前 `scrollOffset` 与中心时间，缩放后还原）。
- 注意：缩放后 `snapTimeFromY`、`getTimeIndicatorOffset` 若仍用固定 `hourHeight` 传参，需改为读当前 `@State` 小时高度。

## 需求 3：长按事件块聚焦态与二级菜单（编辑 / 剪切 / 复制 / 分享）（✅ 代码完成，待设备复验）

> 2026-09-09 设备验收结果：任务包内静止长按约 400ms 后没有显示二级菜单。当前代码虽然已有 `LongPressGesture`、受控 `bindContextMenu` 和部分操作函数，但设备上的菜单展示链路没有生效，而且现有菜单还是“复制、剪切、分享、拉伸”，不符合本次确定的新交互。因此后续应按本节整体重做，不能只修一个弹出开关。

### 一、长按后的整体视觉效果

在周视图或日视图中，对**已安排的事件块**静止长按约 400ms 后进入“聚焦态”：

1. 日历页面的其余内容整体模糊，并叠加轻微暗色蒙层；左侧任务包列表、导航栏、时间标签、其他事件块都属于背景。
2. 被长按的事件块保持清晰，位置和尺寸不跳动；其四周出现约 1~2vp 的蓝色细边框，用于表达“当前选中”。
3. 蓝色边框的上、下边缘同时成为可拖动区域，可直接进入需求 4 的拉伸，不再需要菜单里的“拉伸”入口。
4. 二级菜单显示在选中事件块附近，内容固定为：**编辑、剪切、复制、分享**。菜单应根据屏幕剩余空间自动选择上方或下方，不能被屏幕边缘裁切。
5. 选中事件块、蓝色边框、拉伸手柄和二级菜单均位于模糊层上方，必须保持清晰；背景模糊层不得抢走它们的触摸事件。
6. 在普通聚焦态点击模糊背景可取消选中并关闭菜单。进入剪切/复制待粘贴流程后，背景点击含义改为“选择粘贴位置”，不能再同时触发退出。

### 二、建议的 ArkUI 分层结构

建议在 CalendarTab 页面的最外层使用统一 `Stack` 管理聚焦态，而不是继续让系统 `bindContextMenu` 独自承担所有视觉和状态：

```text
最下层：原日历页面（进入聚焦态后作为被模糊内容）
中间层：全屏背景模糊 + 半透明暗色蒙层 + 背景点击拦截
上层 1：按原坐标重绘的选中事件块（清晰、蓝色细边框、上下命中区）
上层 2：自定义二级菜单
```

- 中间层可使用 ArkUI 的 `backgroundBlurStyle` / `backdropBlur` 对其后方内容做背景模糊，或对原页面层使用 `foregroundBlurStyle`。不能把模糊属性挂到包含“选中事件块副本和菜单”的共同父节点，否则突出内容也会一起变糊。
- 原位置的事件块在聚焦态应隐藏或保持在模糊底层，上层复用同一个事件块 Builder 绘制清晰副本，避免出现两个清晰任务包。
- 模糊接口属于实时渲染能力，性能负载较大。只在 `focused` 状态开启，使用固定且适中的模糊强度；退出聚焦态立即移除，不在缩放、滚动和普通浏览期间长期启用。
- `bindContextMenu` 支持自定义预览和蒙层，但当前受控弹出方案已在设备上失败，而且完整交互还包含背景模糊、选中边框及直接拉伸。优先考虑由页面状态控制的自定义覆盖层和菜单，以便所有元素处于同一坐标与生命周期中。

### 三、长按与滚动的冲突处理

必须保留“任务包内部也可以起手滚动”的现有需求：

1. 手指按下事件块时开始长按候选，但此时不显示蒙层，也不锁定 `Scroll`。
2. 400ms 内移动距离超过允许阈值时，长按立即失败，由父级时间轴继续滚动；该次触摸结束前不得再次弹菜单。
3. 400ms 内没有明显移动时，长按成功，记录当前 `ScheduledEvent.id`，进入聚焦态，并从这一刻起阻止背景滚动。
4. 长按成功后的抬手不能再触发原有短按详情；普通短按仍维持现有详情行为。
5. 后续实现需在实际目标设备上调节移动阈值。项目兼容 API 23，可使用 `LongPressGesture` 的 `duration` 和 `allowableMovement`，但仍须验证它与父级 `Scroll` 的仲裁结果，不能只以编译通过为完成标准。
6. 拉伸手势只绑定到蓝色上、下边缘的独立命中区；事件块主体不得挂一个会吞掉所有纵向滑动的 `PanGesture`。

### 四、统一交互状态，避免多个布尔值互相冲突

建议使用一个主状态表示当前阶段，而不是同时维护多组可能矛盾的 `isShown`：

```text
idle              普通浏览
focused           背景模糊，事件块和菜单突出
stretch-top       正在拖上边缘
stretch-bottom    正在拖下边缘
copy-await-target 已选择复制，等待第一次点击空白位置
cut-await-target  已选择剪切，等待第一次点击空白位置
paste-preview     已显示虚线框，等待框内第二次点击确认
```

与主状态配套保存：`focusedEventId`、待操作日程的深拷贝、剪切时临时隐藏的事件 ID、虚线框日期/时间/位置/高度。每次退出、取消、切换视图或页面销毁时统一清理，避免残留模糊层、隐藏事件或失效菜单。

### 五、菜单功能 1：编辑当前日程实例

#### 交互

- 点击“编辑”后关闭聚焦层，打开任务包编辑页面，并预填充当前**已安排事件**的名称和步骤。
- 保存后返回原来的日历视图和日期，当前事件块立即刷新。
- 事件块右上角显示铅笔 UI，表示它已经偏离母任务包。铅笔需在周/日视图以及聚焦副本中一致显示，并为正文预留右上角空间，不能盖住任务名称。

#### 数据边界

- 这不是编辑 `TaskPackage` 母任务包。现有 `CreatePackage` 的 `packageId` 模式会调用 `taskStore.updatePackage()`，并通过 `syncPackageFields()` 改动所有关联日程，**绝对不能直接沿用该保存分支**。
- 建议为编辑页增加互斥的“日程实例模式”，路由只传 `eventId`；为 `ScheduleStore` 补充 `getEventById()`，进入页面后按 `ScheduledEvent.id` 读取并深拷贝名称、步骤和颜色，保存时只调用 `scheduleStore.updateEvent()`。
- 编辑名称或步骤后，保留该实例原有的 `id`、`packageId`、日期、开始时间和颜色；根据新步骤总分钟数重新计算 `endHour` / `endMinute`。
- `ScheduledEvent` 需要增加可持久化标志，例如可选字段 `isCustomized?: boolean`。旧数据恢复时缺少该字段按 `false` 处理；编辑保存后设为 `true`，用于显示铅笔。
- 母任务包以后再次编辑时，`syncPackageFields()` 不应覆盖 `isCustomized === true` 的日程名称和步骤，否则用户的单实例编辑会丢失。未定制的日程仍可沿用现有级联同步。
- `scheduleStore.updateEvent()` 应通知 CalendarTab 刷新，或返回页面时显式 `loadData()`；不能再次依赖“切换视图后才刷新”。
- 输入校验沿用母任务包编辑页：名称不能为空、至少一个有效步骤、步骤时长合法。所有 `steps` 都必须深拷贝，避免修改日程时污染母任务包或其他同源实例。

#### 铅笔标记语义

- 铅笔表示“这条 `ScheduledEvent` 的内容不是母任务包当前默认内容”，而不是表示母任务包本身被编辑。
- 除手动编辑外，需求 4 的拉伸也会改变实例步骤时长，建议同样将 `isCustomized` 设为 `true`，否则标记语义会与真实数据不一致。

### 六、菜单功能 2：剪切

1. 点击“剪切”后关闭菜单和模糊聚焦态，保存该 `ScheduledEvent` 的深拷贝，并显示气泡提示：**“请点击要粘贴的地方”**。
2. 原事件块应立即从当前视图中消失。为避免用户取消或中断时丢数据，此时只做 UI 层临时隐藏，不立即从 Preferences 删除；仓库中的原事件保留到最终确认。
3. 用户第一次点击周/日时间轴的空白处后，在目标日期和时间显示与原事件块时长等高的虚线框，框中央显示“+”。第一次点击只选择位置，不立刻移动日程。
4. 用户再次点击虚线框内部，才正式更新原 `ScheduledEvent` 的日期、开始/结束时间并持久化；剪切应保留原 `id`。
5. 虚线框出现后，点击另一个空白位置应移动虚线框，而不是直接粘贴；点击已有事件块不应把它当作空白落点。
6. 提供明确的“取消”入口。取消、返回或切换到不支持粘贴的视图时，清除待粘贴状态和虚线框，并让临时隐藏的原事件块恢复；不得造成无提示的数据丢失。

### 七、菜单功能 3：复制

1. 点击“复制”后同样提示“请点击要粘贴的地方”，但原事件块始终保留。
2. 第一次点击空白位置显示带“+”的虚线框；再次点击虚线框内部才确认创建。
3. 确认时基于待复制快照创建新的 `ScheduledEvent.id`，目标日期/时间来自虚线框，其余名称、颜色、步骤及 `isCustomized` 状态保持与来源实例一致。
4. 复制和剪切应共用同一个虚线框 Builder、坐标换算与二次确认逻辑，只根据模式决定“新建 ID”还是“更新原 ID”，避免出现两套落点算法。
5. 该流程需兼容需求 7：同一个母任务包在同一天可以存在任意多个实例，不得再用 `packageId + date` 阻止复制。

### 八、复制/剪切虚线框与需求 8 的关系

- 复制/剪切使用“第一次点击定位、第二次点击确认”的静态虚线框；需求 8 使用“拖动时跟手、松手确认”的动态虚线框。
- 两者交互不同，但必须复用同一套“时间轴局部 Y + Scroller 偏移 - `GRID_LINE_OFFSET` → 分钟 → 当前 `hourHeight` 反算 Y”的几何函数。
- 虚线框宽度应等于目标日期列可用宽度，高度按待操作事件总分钟数映射；边框使用蓝色虚线，中间“+”应可清楚辨认。
- 是否吸附到整点/半点统一遵循需求 8，不能让拖放、复制和剪切分别使用不同的吸附规则。

### 九、菜单功能 4：分享

- 分享对象是当前 `ScheduledEvent` 的实际内容；若它经过单实例编辑或拉伸，应分享修改后的名称和步骤，不能回查并分享母任务包旧内容。
- 使用 HarmonyOS `@kit.ShareKit`：构造 `systemShare.SharedData`，类型使用 `utd.UniformDataType.PLAIN_TEXT`，再由 `systemShare.ShareController` 拉起系统分享面板。
- 文本格式固定为每项一行，不附加内部 ID；当前需求也不要求附加日期与起止时间：

```text
任务名称：xxx
步骤1：xxx（xx分钟）
步骤2：xxx（xx分钟）
步骤3：xxx（xx分钟）
```

- 步骤编号从 1 开始，按事件内 `steps` 顺序生成；名称和时长直接使用日程实例的当前值。分享面板打开失败时给出简短错误提示，并清理聚焦状态。

### 十、需求 3 验收标准

- 任务包内静止按住约 400ms：页面背景模糊，只有该事件块、蓝色细边框、上下边缘和菜单保持清晰。
- 从任务包内部快速上下移动：只滚动时间轴，不弹菜单、不闪烁模糊层；普通短按仍打开详情。
- 菜单严格为编辑、剪切、复制、分享四项，不再出现“拉伸”。
- 编辑只改变当前 `ScheduledEvent.id` 对应实例，母任务包和同源的其他日程不变；返回后立即显示铅笔标记。
- 剪切后源事件视觉消失，第一次点空白处只出现带“+”的虚线框，第二次点框内才完成移动；取消可无损恢复。
- 复制流程相同，但源事件保留，确认后生成独立的新 ID。
- 分享文本逐行符合约定格式，并能正常打开系统分享面板。
- 点击背景退出、取消操作、路由返回及页面销毁后，不残留模糊层、菜单、隐藏事件或虚线框。

## 需求 4：聚焦态直接拖动上下边缘拉伸任务包（✅ 代码完成，待设备复验）

> 2026-09-09 设备验收结果：没有出现可拖动的上下边界。代码中虽有拉伸状态、上下手柄 Builder、`PanGesture` 和等比缩放逻辑，但旧入口依赖菜单中的“拉伸”。新方案取消该菜单项：长按进入需求 3 的聚焦态后，蓝色上、下边缘立即可以拖动。

### 现状

- 事件块创建后时长不可调。

### 目标

- 长按进入聚焦态后，事件块显示蓝色细边框，直接拖动**上边缘或下边缘**即可拉长/缩短。
- 拉长/缩短时，任务包内**所有步骤按各自在总时长中的比例等比缩放**。
  - 例：3 步各 20 分钟（共 60 分钟），缩到 30 分钟时，每步各 10 分钟（×0.5）。

### 边缘视觉与命中区

- 蓝色外观边框建议为 1~2vp，但实际触摸命中区应向事件块内外扩展到约 12~16vp，避免细线难以拖中。
- 上、下命中区只负责纵向拉伸；左右边缘和事件块主体不触发拉伸。
- 开始拖动边缘时可临时隐藏二级菜单，保留背景模糊和选中事件块；松手或取消后回到聚焦态，避免菜单遮住拖动路径。
- 拉伸期间锁定时间轴滚动；退出聚焦态后恢复普通滚动。未进入聚焦态时，边缘命中区不存在，不能破坏任务包内部起手滚动。

### 验收标准

- 长按进入聚焦态后，目标任务包立即出现清晰的蓝色细边框，上、下边缘均能稳定命中，不需要再点击“拉伸”菜单项。
- 手柄区域可以稳定命中，拖手柄时只由拉伸手势接管；普通浏览状态下从任务包主体起手仍可滚动，聚焦状态下主体不会误触发拉伸。
- 上边界拖动保持结束时间不变，下边界拖动保持开始时间不变，并实时预览位置和高度。
- 松手后持久化日程副本并将 `isCustomized` 设为 `true`；所有步骤等比调整且分钟总和严格等于新的日程时长，不修改任务包模板，事件块显示铅笔标记。

### 技术要点

- 拉伸模式由需求 3 的统一交互状态管理，使用 `focusedEventId` 和 `stretch-top` / `stretch-bottom`，不要再额外增加一组彼此独立的菜单入口状态。
- 拖动上边界 → 改 `startHour`/`startMinute`；拖动下边界 → 改总时长。
- **等比缩放步骤**：
  - `ratio = 新总时长 / 原总时长`。
  - 每个 `step.duration = step.duration × ratio`，取整。
- 更新 `ScheduledEvent` 后调用 `scheduleStore` 持久化（已有 `persist()`；若新增 `updateEvent` 方法需同步落盘）。同时同步 `steps`、`endHour`/`endMinute` 冗余字段，避免数据不一致。
- 与需求 1 的绝对定位联动：拖动过程中实时更新事件块的 `top` / `height`。

### 待确认点（重要）

- **取整策略**：非整数比例（如缩到 35 分钟）时，`20 × 35/60 ≈ 11.67` 取整后 3 步之和可能 ≠ 35。建议：各步骤四舍五入后，用**最后一个步骤补齐差额**（`lastStep = 新总时长 - 其余步骤之和`），保证步骤总时长严格等于目标时长。
- **最小步骤时长**：设下限（如 1 分钟），避免步骤被缩到 0。
- **是否修改 `steps` 内部时长**：本需求明确「是」——等比缩放 `steps` 各步骤时长，并同步 `endHour`/`endMinute`。需保证与「任务包模板」（`TaskPackage.steps`）的关系：拉伸的是「日程」（`ScheduledEvent.steps` 冗余副本）还是「任务包模板」本身？建议只改日程的冗余 `steps`，不动 `TaskPackage` 模板，避免一次拉伸污染模板。

## 需求 7：同一天允许重复安排同一个任务包（✅ 已完成）

### 当前限制

`CalendarTab.handleDrop()` 会调用 `scheduleStore.isPackageScheduledOnDate(pkgId, dateStr)`；只要同一 `packageId` 在同一天已有一条日程，就直接提示“已安排在此日期”并拒绝创建。因此当前无法在一天内重复使用同一个任务包。

### 目标

- 同一个任务包在同一天可以安排任意多次，不做“任务包 ID + 日期”唯一性限制。
- 每次安排都创建独立的 `ScheduledEvent.id`，拥有各自的开始时间、结束时间和步骤副本。
- 后续移动、删除、拉伸其中一条日程时，不影响同日的其他实例，也不修改任务包模板。
- 若多个实例时间重叠，先允许按现有规则重叠显示；并排避让可作为独立需求处理。

### 后续实现要点

- 移除 `handleDrop()` 中的 `isPackageScheduledOnDate()` 拦截。
- 检查复制、剪切、持久化、编辑同步和删除逻辑是否始终以 `ScheduledEvent.id` 区分实例。
- `ScheduleStore.isPackageScheduledOnDate()` 若没有其他调用方，再决定删除或保留为查询接口。

### 验收标准

- 把同一个任务包连续拖到同一天的三个不同时间，三条日程都能创建并在重启后保留。
- 删除或移动其中一条时，另外两条不发生变化。

## 需求 8：任意时间拖放、虚线框预览与整点/半点磁吸（✅ 代码完成，待设备复验）

### 当前限制

- 当前 `snapTimeFromY()` 无条件把落点四舍五入到最近半小时，不能在其他分钟自由放置。

### 目标交互

1. 任务包拖入周/日时间轴后，在手指所在日期和时间位置的下层显示虚线占位框。
2. 占位框高度等于任务包总时长映射后的高度，位置随手指和当前缩放倍率实时移动。
3. 默认允许落在任意时间；接近整点或半点刻度若干 vp 时产生磁吸，虚线框自动贴到 `HH:00` 或 `HH:30`。
4. 离开磁吸范围后恢复跟手移动，而不是始终强制按半小时取整。

6. 拖拽取消或离开时间轴时清除虚线框；靠近视口上下边缘时是否自动滚动需在实现时一并评估。

### 建议状态与坐标

- 保存预览日期、原始分钟、最终吸附分钟、预览 Y、预览高度和是否处于磁吸状态。
- 坐标统一采用 `手指局部 Y + Scroller 偏移 - GRID_LINE_OFFSET`，再除以当前 `hourHeight` 换算分钟。
- 磁吸阈值应以 vp 定义（例如 6~10vp，最终以设备手感确定），分别计算到最近整点和半点的像素距离。
- 非磁吸状态的最小时间粒度需后续确认；建议先采用 5 分钟，既接近自由放置，也便于显示和编辑。

### 验收标准

- 在不同缩放倍率和滚动位置拖动时，虚线框始终紧跟同一时间坐标，不出现漂移。
- 接近整点/半点时能明显吸附，离开阈值后立即解除吸附。
- 松手后的任务包顶部与最后一次虚线框位置完全一致。
- 同一任务包可结合需求 7，在同一天重复拖放多次。

## Bug：已完成任务的“查看结果”页面不可操作，也无法重新开始（✅ 已解决，详见 `log_13.md`）

### 现象

- 日程中的任务包完成一次后，再次打开详情，主按钮从“开始任务”变为“查看结果”。
- 点击“查看结果”会再次进入计时页面，但该执行记录已经处于 `completed` 状态，因此倒计时不会运行。
- 上一步、下一步等步骤切换操作对已完成记录无效，也没有“重新开始”入口，用户只能查看一个无法继续操作的计时页面。

### 当前原因

`ScheduledEventDetailDialog.startOrContinue()` 无论按钮文案是什么，都会调用 `executionStore.startFromScheduledEvent()`。该方法发现同一 `ScheduledEvent.id` 已有执行记录时，会直接返回最新记录；完成记录因此被原样传给 `ExecutionPage`。现有执行仓库也没有为同一日程创建新一轮执行的方法。

### 原规划（已由本轮产品决策取代）

1. 明确“查看结果”页面需要展示哪些完成信息；结果页不应伪装成仍可计时的执行页。
2. 在结果页或详情页提供独立的“重新开始”入口，为同一日程创建新的 `ExecutionSession`，不能复用已完成记录。
3. 调整 `startFromScheduledEvent()` 的语义或新增专用方法，使“继续未完成任务”“查看历史结果”“创建新一轮执行”成为三条明确路径。
4. 验证重新执行后，日历上的完成标记如何定义：建议只要该日程至少成功完成过一次就保持已完成，新的进行中记录不应抹掉历史完成状态。

### 验收标准

- 点击“查看结果”能看到稳定的完成结果，不出现静止倒计时和失效步骤按钮。
- 用户可以明确选择“重新开始”，新一轮倒计时从第一步完整时长开始。
- 新旧执行记录互不覆盖，退出并重启应用后仍可正确区分。

### 最终解决方案

- 不再制作独立结果页；终态会话的详情按钮从“查看结果”改为“再次开始”。
- 再次开始会创建新的 `ExecutionSession`，从第一步完整时长进入计时页；上一轮记录继续保留。
- 日历标题按同一 `ScheduledEvent.id` 的正常完成记录累计显示“任务包标题 · 已完成 x 次”；放弃记录不计数。
- 正在运行、暂停或等待下一步的会话仍显示“继续任务”，不会误建重复会话。
