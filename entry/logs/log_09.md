# 鸿蒙应用第九次开发日志

## 项目信息

- **项目名称**：StudyStream
- **开发日期**：2026-09-03
- **目标**：修复周/日视图时间轴的分割线对齐与 24:00 底部留白（遗留自 `log_07` / `left_problem.md`）

---

## 一、问题背景

`log_07` 通过「动态高度数组」把分割线对齐推到了「基本可接受」，但 `left_problem.md` 记录了两个仍未彻底解决的问题：

1. **分割线对齐**：左侧时间标签（`00:00`~`24:00`）与右侧内容区的水平分割线存在 1-2vp 的字体 ascender 微偏，且周/日视图的魔法 padding 不一致。
2. **24:00 底部留白**：24:00 标签下方仍有可见灰色留白，灰色背景没有紧贴 24:00 标签截止。

期间曾尝试 **Canvas 自绘时间轴网格** 方案（编译通过），但出现「分割线完全不显示」和「24:00 被挤出渲染区域」两个新问题，遂放弃。本次回到**纯布局**方案，从根因上修复。

---

## 二、根因分析

排查后定位到三个相互纠缠的根因（都在 `CalendarTab.ets`）：

1. **`Divider()` 子元素占 1vp 布局空间**：原实现每个小时槽位 = `Divider(1vp)` + 事件块/`Blank(H-1)`，比左侧标签槽位（纯 `H`）多 1vp，24 小时累计漂移 23vp。此前靠 `heights.push(maxH + 1)` 和 `Blank(H-1)` 硬补偿。

2. **槽位 `Column` 没有显式高度**：有事件的小时槽位高度 = 事件块实际高度，可能小于同小时其他天的最大高度 `heights[h]`，导致不同天之间的下一条分割线不在同一水平线（隐藏 bug，此前未暴露）。

3. **25 个槽位里包含 `24:00`**：时间轴本应是「24 个内容槽位（00:00~23:00）+ 24:00 作为终点边界」。原实现把 24:00 也当成一个完整槽位（`heights[24]` = 60vp），于是 24:00 标签下方多出整整一个槽位高度的灰色空间——这正是「24:00 底部留白」的真正来源，**与 padding 无关**。

此外，日视图外层 `Row` 漏设 `alignItems(VerticalAlign.Top)`（默认 `Center`），两列高度不一致时会被整体居中错位。

---

## 三、方案与改动（全部在 `CalendarTab.ets`）

### 1. 分割线改用 `border`，不占布局空间

用 `.border({ width: { top: 1 }, color: '#E0E0E0' })` 替代槽位内的 `Divider()` 子元素。`border` 画在盒子边缘、不参与布局，槽位高度不再需要 `+1` 补偿。

### 2. 槽位显式固定高度

给每个小时槽位 `Column` 加 `.height(heights[h])`，保证同一天/不同天同一小时槽位高度严格相等，分割线（槽位顶边）天然对齐。

### 3. 高度数组去掉 `+1`

`computeWeekHourHeights` / `computeDayHourHeights` 的 `heights.push(maxH + 1)` 改为 `heights.push(maxH)`，并同步删除 `Blank().height(heights[h] - 1)` 中的 `-1`（实际上 Blank 已整体移除）。

### 4. 24:00 从「独立槽位」改为「末尾边界」

- 高度数组从 25 个元素减为 **24 个**（`h < WEEK_END_HOUR - 1` / `h < 24`）。
- 时间标签列：`ForEach` 只渲染 00:00~23:00 共 24 个，末尾追加一个 `Text('24:00')`（自然高度，文字顶紧贴内容区底边分割线）。
- 内容列：24 个槽位（00:00~23:00），末尾用 `.border({ width: { bottom: 1 } })` 画 24:00 分割线。

### 5. 统一 padding + 修正对齐

- 4 处 padding（周/日视图的标签列、内容列）全部归零，消除不对称。
- 日视图外层 `Row` 补上 `.alignItems(VerticalAlign.Top)`。

### 6. 吸附偏移同步

`snapTimeFromY` 中硬编码的 `- 5`（旧内容列 `top: 5` 的补偿）随 padding 归零一并去掉。

### 7. 分割线下移消除 ascender 微偏

`Text` 字形因 ascender 不从 y=0 开始，导致分割线相对标签「上偏」。最初尝试用 `.offset({ y: -3 })` 上移标签文字，但会让 00:00 顶部被裁剪，遂改为**下移分割线**：内容列槽位从 `border-top`（y=0）改为 `Blank(3)` + `Divider`（分割线落在 y≈3），槽位高度随之 `+4`（3vp 空隙 + 1vp 分割线）。标签文字保持在槽位顶部不动，字形（y≈3）与分割线（y=3）自然对齐。

## 七、已知限制与后续

- **字体 ascender 微偏（已用分割线下移补偿）**：`Text` 字形因 ascender 不从 y=0 开始，已通过「内容列槽位顶部加 `Blank(3)` + `Divider`」把分割线下移 3vp 对齐到字形。空隙值 3vp 是估算值，若个别字体下仍有细微偏差，微调 `Blank(3)` 的高度即可；若追求像素级 ±0，仍需 Canvas（`fillText` + `textBaseline` 精确控制字形基线）。
- **时间指示线精度**：`getTimeIndicatorOffset` 仍用固定 `hourHeight` 累加，未按动态 `heights` 计算，有事件撑高槽位时红色「现在」线会略偏（既有问题，本次未动）。
- **拖拽吸附精度**：`snapTimeFromY` 同样用固定 `hourHeight`，多事件重叠的小时吸附会略偏（既有问题）。

---

## 八、关键结论

> 时间轴的「对齐」问题本质上不是像素微调，而是**布局结构**问题：`Divider` 占空间、槽位无固定高度、24:00 被错当成内容槽位。把这三处结构理顺后，对齐和底部留白不靠任何魔法数字即可解决；最后残留的 ascender 微偏，用一个 `offset({ y: -3 })` 即可补偿，无需引入 Canvas。
